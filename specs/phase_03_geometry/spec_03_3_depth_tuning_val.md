## Objective
Choose the estimator and the depth parameters from data, **on SUN val only**, and show whether the status flag means something (flagged objects should have larger error). The test-split 3D numbers are **not** computed here; they belong to Phase 05, with these choices frozen.

## Requirements
- **R1. GT 3D centres.** For each SUN GT object, the centre is `Box3D.centroid_cam(Rtilt)` (OpenCV camera frame). Linking 2D GT boxes to 3D boxes: use the `has3d` linkage from the annotation parser if its ordering is verified to be 1:1 on a sample of 20 images (projected 3D box vs 2D box IoU ≥ 0.5 for each pair); otherwise link by projecting each 3D box to the image and taking the best 2D IoU. The method used and the verification count are recorded.
- **R2. Two input modes,** so detection errors and depth errors are separated:
  - **Oracle boxes:** GT 2D boxes of mapped classes (depth error only).
  - **Detected boxes:** the stored `sun_val_full` detections at `conf_operational`, matched to GT per `docs/evaluation_protocol.md` §3 (same class, highest IoU ≥ 0.5, greedy by score).
- **R3. Metrics** (per protocol §3), over objects with status `valid`: depth error `|Ẑ − Z_gt|` (MAE, RMSE), signed mean `Ẑ − Z_gt`, 3D centre error (median, mean, p90). Broken down by distance bucket (0–2, 2–4, > 4 m) and by sensor. The status fractions (`valid` / `low_coverage` / `no_depth`) and the error of `low_coverage` objects are reported separately.
- **R4. Known bias.** The GT centre is a volume centre, our estimate a visible-surface point. Report the signed bias; the "surface-corrected" variant (adds half the GT depth extent along the viewing ray) is shown **only as analysis**, never as the headline.
- **R5. Search space (fixed now, before looking at results):**
  - estimator ∈ {A median, B nearest mode};
  - shrink s ∈ {0.3, 0.4, 0.5, 0.6, 0.7};
  - inlier k ∈ {1.5, 2.0, 3.0};
  - B bin width ∈ {2.5, 5, 10} cm, m_frac ∈ {0.1, 0.15, 0.25}.
  **Selection objective:** minimise the **median 3D centre error** on oracle boxes with status `valid`, subject to the `valid` fraction ≥ 0.6. Ties within 5 mm → prefer the simpler choice (A over B, larger s).
- **R6. Status thresholds** (N_min, τ_cov, τ_spread), chosen after R5: pick τ_spread and τ_cov so that `low_coverage` objects have a clearly higher median error than `valid` ones (report the ratio), while keeping ≥ 60% `valid`. N_min is fixed at 20 unless val shows that objects with 20–50 valid pixels have > 2× the median error.
- **R7. Outputs.** `benchmarks/geometry/tune_val.json` (every configuration evaluated, with counts), the chosen values written to `configs/depth.yaml` with the source noted, and `docs/depth_tuning.md` generated by a script (do-not-edit header), including a 3D error gallery of the 12 worst val objects with an explanation category (background bleed, thin structure, GT box issue, missing depth, …).
- **R8. No test peeking.** The script refuses to run on any split other than val (`--split` accepts only `sunrgbd_val`).

## Acceptance criteria
- **AC1.** R1 linkage verified and the method recorded.
- **AC2.** Full grid evaluated on val (oracle and detected modes); the chosen configuration and the reason (objective value, valid fraction) are stated.
- **AC3.** The status flag is shown to be meaningful: `low_coverage` median error / `valid` median error is reported (expected > 1; if it is not, that is reported as a finding and the flag design is revisited before Phase 05).
- **AC4.** Bias reported with sign; surface-corrected numbers labelled as analysis only.
- **AC5. Phase 03 exit.** 03.1 and 03.2 ACs hold; all tests pass; `configs/depth.yaml` has no remaining placeholder values; test split untouched (the script's guard plus a note in `PROGRESS.md`).

## Tests (`tests/test_localization.py`)
- A synthetic scene with known 3D boxes and a rendered depth map → oracle-mode centre error ≈ the analytic surface-vs-volume offset.
- Linkage: projected 3D box of a known cube gives the expected 2D box.
- Bucketing edges (exactly 2.0 m and 4.0 m go to the documented bucket).
- Split guard rejects `sunrgbd_test`.

## Results (Measured, SUN RGB-D val, 528 images; run 2026-11-10, second R5 pass 2026-11-11)
Full tables: [docs/depth_tuning.md](../../docs/depth_tuning.md) (generated by `scripts/tune_depth.py`; raw numbers in `benchmarks/geometry/tune_val.json`). These are tuning numbers on val, not headline results.

**Review decision (2026-11-11): R5 runs twice.** Iteration 1 chose shrink under the placeholder thresholds (tau_spread 0.25 m), and these excluded shrink 0.6/0.7. R6 then loosened tau_spread to 0.5 m. So R5 was re-run once at the iteration-1 R6 thresholds, then R6 again. That is one extra pass only, with no loop to convergence; R6 moved again (tau_cov 0.2 → 0.3) and this is reported, not iterated.

| | Iteration 1 | Iteration 2 (frozen) |
|---|---|---|
| Configuration | A, shrink 0.5, k 3.0 | **A, shrink 0.7, k 3.0** |
| Thresholds (n_min / tau_cov / tau_spread) | 20 / 0.2 / 0.5 m | **20 / 0.3 / 0.5 m** |
| Oracle valid fraction | 0.89 | 0.81 |
| Oracle valid median error | 31.4 cm | 28.2 cm |
| Detected valid median error | 26.8 cm | 24.6 cm |

The gain is not only from scoring fewer objects. On the same objects, shrink 0.7 is better than 0.5:
- oracle objects valid under both settings (n = 1354): 28.2 vs 29.2 cm;
- all oracle objects with depth (n = 1693): 29.9 vs 32.4 cm;
- detected objects with depth (n = 865): 26.5 vs 28.0 cm.

The cost is a lower valid fraction, 0.81 vs 0.89.

- **AC1 ✅** The `has3d` order failed the R1 check on full val (2145/3044 pairs at IoU ≥ 0.5), so projection linkage is used (same class, Hungarian on IoU, IoU > 0). 2969 of 3117 3D boxes are linked; 1705 are in mapped classes. 14.6% of the oracle links have IoU < 0.3.
- **AC2 ✅** 150 configurations, oracle and detected, in both iterations. Final: estimator A, shrink 0.7, k 3.0 (28.4 cm at valid fraction 0.82 under the iteration-1 thresholds). A and B agree within 1 mm, and k = 3 is best everywhere. tau_spread 0.5 m is the edge of the grid. n_min stays 20: the 20–50 px vs ≥ 50 px ratio is 1.70 with n = 2, so this is not evidence.
- **AC3 ✅ (weak)** The low_coverage/valid median error ratio is 1.45 for oracle and 1.70 for detected. Status (oracle, n = 1705): valid 0.81, low 0.19, no_depth < 0.01.
- **AC4 ✅** Valid objects, oracle: median 28.2 cm, mean 38.7 cm, p90 84.8 cm; Z MAE 28.4 cm; signed Z −9.7 cm (the estimate is nearer than the volume centre). Detected (n = 710 valid): median 24.6 cm, signed Z −3.4 cm. By distance (oracle): 0–2 m 23.7 cm, 2–4 m 31.9 cm, > 4 m 35.8 cm. Surface-corrected (analysis only) overshoots: median 53 cm. It moves the GT to the nearest box corner rather than to the visible surface, so it is not used.
- **AC5 ✅** 03.1 and 03.2 ACs hold, with the timing bound restated (see the 03.1 R9 decision); 119 tests pass; `configs/depth.yaml` has no placeholders; `require_tuning_split` refuses everything except `sunrgbd_val`, and `PROGRESS.md` notes this.

**Findings**
1. The error floor comes from the GT definition (amodal volume centre vs visible surface) and from link noise, not from the estimator. Keeping only links with IoU ≥ 0.3 gives a median of 26.3 cm. Worst-12 gallery (second pass): 5 occluder in box, 4 background bleed or thin structure, 1 background bleed with link mismatch, 2 GT box issue.
2. R6 did not settle after the extra pass (tau_cov moved 0.2 → 0.3). The rules allow only one extra pass, so the second-pass values are frozen. Fine re-tuning on val would just fit to the val set.
